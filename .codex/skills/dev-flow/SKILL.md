# 開発フロー（Codex）

meme-gtd の Task を起点に、検討 → 計画 → 実装 → 確認 → PR → レビューを直列に進める手順。このスキルがこの流れの唯一の正。

## 窓口の仕事

メインスレッド（窓口）が行うのは、次の4つだけ。

- ユーザーと話す（報告、合意の確認、質問）
- `scripts/task.mjs` で Task を読み、記録する
- 担当役を `spawn_agent`（`fork_turns="none"`）で起動し、完了を待ち、結果を次の担当役とユーザーに渡す
- ローカルの `main` を最新にする（`git fetch origin main` と `git merge --ff-only origin/main`）。担当役に回さない。担当役の承認依頼は担当役のスレッドに出て、iPhone からの操作では表示されない（Task 2114 では、担当役が `git fetch` と `git merge --ff-only` の承認待ちで、それぞれ約1時間止まった）

調査、コードの読み取り、Web 検索、画面の操作、撮影、画像の点検、確認一覧の点検、編集、ビルド、テスト、push、PR 作成、マージの確認は、すべて担当役に渡す。窓口は自分で行わない（同じ文脈で続けると、検討時の誤った前提が実装とレビューまで残り、窓口の文脈も膨らむため）。

- 担当役を待つときは、`wait_agent` を `timeout_ms=3600000` で呼ぶ（短い値を渡しても、`.codex/config.toml` の設定で1時間に引き上げられる）。担当役の完了とユーザーの発言で待機は終わる。短い時間で待ち直さない（Task 2107 では60秒の待機を52回繰り返し、そのたびに窓口の文脈全体を送り直した）。
- 待機が終わったら、届いたものを読む。担当役の完了報告なら次へ進む。完了報告でなければ、もう一度同じ形で待つ。
- 途中経過を取りに行かない（`send_message` での問い合わせ、確認一覧の読み取りなど）。担当役の完了報告だけで次へ進む。
- 担当役の作業を止める（`interrupt_agent`）のは、ユーザーが止めるよう指示したときだけ。

`.codex/hooks/orchestrator-guard.mjs` が、窓口のこれ以外の操作を拒否する。拒否されたら、担当役に渡す。

### 最初に（フックの確認）

フックは、ユーザーが Codex の **Settings > Hooks**（CLI は `/hooks`）で信頼するまで実行されない。フックの定義を変えると、信頼は外れる（Task 2107 では一度も実行されていなかった）。受付の最初に、次のコマンドを1回実行する。

```bash
echo dev-flow-hook-check
```

- 拒否された: フックは有効。そのまま進める。
- 実行されて文字列が表示された: フックは無効。最初の報告の末尾で、「dev-flow のフックが信頼されていません。Settings > Hooks で信頼をお願いします」と1回だけ伝える。作業は止めず、このスキルの決まりを自分で守って進める。

## 発言の受け取り方

ユーザーの発言に応える前に、毎回確かめる（`.codex/hooks/user-prompt.mjs` が発言ごとに同じ内容を渡す）。

1. **質問には、最初に答える。** 「答えろ」「これ何？」「何やってる」に対しては、答えだけを返す。答える前に操作しない（担当役の停止、調査、Task への記録も後にする）。
2. **「は？」や短い否定は、直前の窓口の出力への異議。** 直前の出力と元の依頼を読み直し、何を外したかを特定して直し、元の依頼を続ける。取り下げ・拒否・新しい作業の指示に読み替えない。何を外したか分からないときだけ、どの点かを1問で聞く。
3. **行うのは、言われたことを、言われた範囲で。** 「実機に入れろ」「サーバーを立ち上げ直せ」のような指示は、その操作を済ませてすぐ報告する。頼まれていない確認や調査を続けて、報告を遅らせない。
4. **頼まれた成果物だけを作る。** 「整理して報告しろ」への成果物は、このチャットでの報告。Task の起票、サブ Task への分割、指摘一覧の作成に読み替えない。Task の起票は、ユーザーが「作れ」と言ったときだけ行う。
5. **決まっていることを聞き返さない。** Task の本文とユーザーの発言に書いてある対象・挙動は、前提として進める。調査で分かることは、聞かずに担当役に調べさせる。
6. **報告や設問を直すときは、指摘された箇所だけを直す。** 前の版にあった項目・列・件数を減らさない。
7. **ユーザーの言葉と、このスキルの語を使う。** 自分で作った用語や、外部資料の用語で言い換えない。スキルの規定に触れるときは、該当箇所を読み直して、そのまま引く。
8. **Task の本文にある例を、要件の範囲にしない。** 「たとえば」「〜とか」で書かれたものは例。Why と What に書かれた要求の全体を対象にする。
9. **原因や状況を聞かれたら、自分の出したものが機能したかどうかを最初に書く。** 周りの事情は、結論を変えるときだけ書く。
10. **ご指摘を受けたら、反省の文を返さない。** 「指摘一覧」に記録し、その行動を続ける。

## 止まってよい場所

ターンを終えてよいのは、次の3つだけ。

- 検討結果への合意を待つとき（2）
- 計画への合意を待つとき（3）
- 依頼された作業が完了し、その報告をしたとき

それ以外では止まらない。合意を待つときは、判断に必要な内容をこのチャットに書いたうえで、最後に、何への合意を求めているかを1文で書く（結果だけを書いて黙って終わらない）。

合意が要るのは、検討結果と計画の2つ。**実装結果の確認、PR のレビューは別のもの**で、検討結果や計画への合意の代わりにならない。合意の後は、PR とレビューの報告まで止まらずに進める。

## チャットでの報告

ユーザーが読むのは、このチャット。Task への記録は作業ログで、報告の代わりにならない。「Task に記録しました」で済ませず、判断に必要な内容をチャットに書く。

- 最初の1文は、ユーザーの問いへの結論にする。
- 依頼された操作が終わったら、その時点で報告する。
- ご指摘への対応を報告するときは、指摘一覧と同じ項目（番号・場面・ご指摘の原文・やることか守ること・状態・証拠）で書く。原文を自分の言葉に置き換えない。「一部対応」のような曖昧な状態は使わず、行を分ける。
- Codex の画面では表を使ってよい。Task のコメントには表を使わない（iOS アプリは Markdown の表を表示できず、`task.mjs` も投稿を拒否する）。
- 画像は `![何の画面のどの状態か](絶対パス)` で添える（ユーザーはリモートから見ていることが多く、ファイルへのリンクは開けない）。出すのは、確認役が点検を済ませて返した画像だけ。

## 質問の形

聞くのは、「どうあるべきか」（挙動・見た目・名称・対象範囲・やらないこと）のうち、Task とユーザーの発言で決まっておらず、調査しても決められないことだけ。次のことは聞かない。

- Task の本文やユーザーの発言に書いてあること
- 調査やコードの確認で分かること（調べてから出す）
- 起きていない場合の仮定の話
- 窓口や担当役の進め方（自分で決めて進める）

聞くときの形:

1. 決めることが複数あるときは、まず何を決めるかの一覧をユーザーと合意する。合意の前に選択肢を出さない。
2. 合意した項目ごとに、`request_user_input_async` で1問ずつ出す。範囲を決める問いを、順番を決める問いより先に出す。
3. 設問には、何が起きたか（背景）を一目で分かる長さで書く。選択肢ごとに、効く点と弱い点を書く。選択肢は、調査で確かめた事実に基づくものだけにする。
4. 選択肢に「推奨」の印を付けない。別々に決めるべきことを1つの選択肢にまとめない。
5. 見た目を決める問いには、該当画面のスクショを添える。

自分の誤りの直し方は、ユーザーに選ばせない。依頼どおりに直してから報告する。

## 指摘一覧

ご指摘は、Task の固定コメント1件（`## 指摘一覧`）に、**場面**と、それに対する**行動**か、以降の行動の**制約**として記録する。発言を写すだけの行は作らない。操作は `scripts/task.mjs status` だけを使う（引数は `task.mjs help`）。

- **場面**: 直前に窓口が何を出し、何をしたか。応答の一部を選択しての指摘なら、選択された文を引く。Task の本文にある要求なら「Task 本文 What」と書く。
- **指摘**: ユーザーの原文。
- **行動**: この指摘に対してやることと、何が出来ていれば完了か。
- **制約**: 以降ずっと守ること。進め方への指摘は制約にする。守ったかを次の操作で判定できる形で書く（「気を付ける」ではなく「合意待ち以外でターンを終えない」）。
- 1つの発言が行動と制約の両方を含むときは、2行に分ける。同じことを再び指摘されたら、行を増やさず `status again` で記録する。
- 有効な制約は、フックが開発者向けの文脈として渡す（制約が変わった後の発言、会話の圧縮後、担当役の起動時）。**次の操作と報告の前に、渡された制約の全件に照らす。** フックが動いていないときは、`status add / again / set` が代わりに表示する。
- 同じことを再び指摘された制約は、この Task の中だけでは防げていない。最後の報告（7）に、「`AGENTS.md` かスキルに上げる規則の候補」として挙げる。上げるかどうかはユーザーが決め、上げると決まったら実装役が追記する。
- `task.mjs read` を呼ぶのは、受付時だけ。記録のたびに読み直さない（Task 2122 では読み直しの出力が合計21万文字になった）。
- 状態を持つのは行動だけ。`完了` は、完了の条件を満たした証拠（チャットで報告した内容、出した画像、テスト名、コミット）があるときだけ。ユーザーに却下された成果は証拠にならず、`again` で対応中に戻す。状態の表示を指摘されて、表示だけを書き換えない。
- `対象外` と制約の `解除` は、ユーザーがそう決めたときだけ。
- 受付時に `status init` で作り、Task の本文とコメントにある要求を行動として記録する。作るのは、このフローで進めている Task だけ。

## Task への記録

`scripts/task.mjs` だけを使う（使い方: `node .codex/skills/dev-flow/scripts/task.mjs help`、詳しくは `references/task-log.md`）。`curl` で API に直接書き込まない。Task の Body と status は、ユーザーの指示があるときだけ変更する。Task の起票（`task.mjs create`）は、ユーザーが作るよう指示したときだけ行う。

## 1. 受付

1. フックを確認する（「最初に」）。
2. `task.mjs read` で、Task の本文・コメント・リンクを全部読む。貼られた JSON より、Task の現在の内容を正とする。
3. `task.mjs status <TaskID> init` で指摘一覧を作り、ご指摘を原文のまま追加する。
4. 開始地点を決める。
   - 依頼が検討や調査を求めている（「検討から始める」など）: 2 へ進む。
   - 依頼が実装を求めている（「実装」「直して」「作って」など）: 3 へ進む。
   - 依頼が Task の作業ではない（「整理して報告しろ」など）: 頼まれた成果物だけを作る。必要な調査は担当役に渡し、結果をチャットで報告する。
   - どれとも読み取れない: 2 の調査を始めながら、検討と実装のどちらかを1問で聞く。

## 2. 検討

目的は、どう実現するかの方式を調べ、ユーザーと合意すること。ファイルは変更しない。

1. 計画役を起動し、`roles/planner.md` の「検討の調査」を依頼する。渡すのは Task ID だけ。
2. 計画役の報告を、このチャットに次の項目で書く。
   - **前提**: Task の本文とユーザーの発言で決まっている対象・挙動（聞き返さない）
   - **比べた方式**: 方式ごとに、できることと弱い点
   - **採る方式と理由**
   - **影響**: 採る方式が、対象の外に及ぼす変化（同じ API や画面を使う他の箇所）。API・DB・同期の仕様に変更が要るかどうかを、必ず書く。要るなら「API の仕様変更が必要」と明記する
   - **誰が何を確かめたか**: 読んだコード、Web で確認した資料
   - **決める必要があること**: 「質問の形」に当てはまるものだけ。無ければ「なし」
3. 最後に「この方式で計画に進めてよいですか」と聞いて、合意を待つ（止まってよい場所）。決める必要があることが残っていれば、「質問の形」に従って聞く。

新しい画面や表示を検討するときは、文章の案より先に、計画役が作った**案の画面**を出す。現行画面のスクショは案の画面ではない（Task 2122）。案の画面は、色・フィルタの形と位置・操作をまとめる場所・右側パネルを、同じ種類の既存画面のコンポーネントどおりにし、長いタイトルと長い本文の項目を入れて、既存画面と見比べてから出す。

スクショは、ユーザーが見た目を見て決めることがあるときだけ、計画役に撮らせて添える。ユーザーが Task に書いた現状の表示を、撮って見せ直さない（Task 2107 では、判断に使わない現行画面を3枚撮り直して提出した）。

## 3. 計画

検討結果への合意を得てから始める。実装の依頼から始まった場合は、ここから始める（計画役が 2 の調査も合わせて行う）。

1. 計画役を起動し、`roles/planner.md` の「計画」を依頼する。渡すのは Task ID と、検討で合意したことだけ。
2. 計画役は、計画を `task.mjs comment --kind plan` で Task に記録し、同じ内容を窓口に返す。
3. 計画を、このチャットに次の項目で書く。要求の言い直しではなく、どう実現するかを書く。
   - **変更箇所**: どのファイル・処理を、どう変えるか
   - **処理の順序や条件**: その順序・条件にする理由
   - **確認すること**: 自動テストで確かめること、実画面で確かめること。既存の E2E シナリオからどれを選び、なぜ選んだか
   - **仕様判断**: 挙動・見た目・名称・対象範囲を、Task とご指摘に無い形で決める必要があるか
4. 合意を取る。
   - 検討から始まった依頼: 「この計画で実装に進めてよいですか」と聞いて、合意を待つ（止まってよい場所）。計画に仕様判断が無くても、合意を待つ。
   - 実装の依頼から始まり、仕様判断が無い: 計画をチャットに書いたうえで、止まらずに 4 へ進む。
   - 実装の依頼から始まり、仕様判断がある: 「質問の形」に従って聞き、合意を得てから 4 へ進む。

サブ Task への分割は、ユーザーが分けると決めたときだけ行う。

## 4. 実装（実装役）

1. 実装役を起動し、`roles/implementer.md` を読ませる。渡すのは対象の Task ID だけ。
2. 実装役は、実装・自動テスト・push 前の検証まで行い、計画の「確認すること」から確認一覧（JSON）を作って返す。画面の確認は、確認役が行う。
3. 実装役の報告に、ゴールの範囲外の気づきがあれば、最後の報告（7）に含める。

## 5. 確認（確認役）

1. `spawn_agent` で `agent_type="verifier"`・`fork_turns="none"` を指定して確認役を起動する。渡すのは Task ID、実装のブランチと worktree のパス、確認一覧のパスだけ（実装役の説明は渡さない）。
2. 確認役は、確認一覧の全行を実画面で操作し、結果とスクショを記録し、画像を自分で点検して返す。全行がそろうまで、`.codex/hooks/verifier-stop.mjs` が終了を差し戻す。
3. 確認役の報告に `fail` があれば、その行を実装役に戻す。修正後は、確認役を新しく起動して全行を確認し直す。
4. 全行が `pass` になったら、止まらずに 6 へ進む。ユーザーの確認を待たない（スクショは 7 の報告で出す）。

## 6. PR（実装役）

1. 実装役に push と PR 作成を依頼する。このフローで実装に進んだ時点で、PR 作成までが依頼に含まれる（`release` スキルの「Push は明示的な指示がある場合のみ」は、この依頼で満たされる）。
2. ベースは `main`。push 前の検証は、ルート `CLAUDE.md`「Push前のローカル検証」に従う。
3. 窓口が `task.mjs link-pr <TaskID> --url <PR URL>` で、Task に外部リンク（表示名 `PR`）を登録する。

## 7. レビュー（レビュー役）と報告

1. レビュー役を起動し、`roles/reviewer.md` を読ませる。渡すのは PR 番号と Task ID だけ。レビュー結果は、レビュー役が `task.mjs comment --kind review` で記録する。
2. レビューの指摘のうち、確認基準を満たしていない不具合は、実装役に直させ、5 の確認からやり直す。それ以外の指摘（確認の追加の提案、範囲外の気づき）は、追加の作業を始めずに、報告に含める。
3. 指摘一覧を更新し、このチャットに報告する。
   - PR の URL
   - ご指摘ごとの状態（「チャットでの報告」の形）
   - UI の変更を含む場合は、変更後の画面のスクショ（確認役が点検済みのもの。対象が複数あれば対象ごとに1枚）
   - レビューの指摘と、その扱い
   - 再発した制約（`AGENTS.md` かスキルに上げる規則の候補）。無ければ書かない
   - ユーザーが普段の環境（実機、ポート3000）で変更を見るために必要なこと（「実機」の節）

## 8. マージ後

ユーザーが「merged」と伝えたら、次を行い、結果を報告する。1 は実装役に依頼する。2 は窓口が自分で行う（「窓口の仕事」）。

1. `gh pr view` でマージを確認する。
2. ローカルの `main` を `origin/main` まで更新する。「merged」と言われたターンの中で行い、後回しにしない（PR 281 では、マージ後にローカルを更新しなかったため、次の Task 2122 が古いフローで動いた）。作業ツリーに未コミットの変更や未追跡のファイルがあっても、それらを残したまま更新する（`git pull --ff-only`。変更中のファイルが更新と重なって失敗したときだけ、止めて報告する）。
3. マージした変更が `.codex/` か `AGENTS.md` を含むときは、ローカルの `.codex/skills/dev-flow/SKILL.md` がマージ後の内容になっていることを確かめる。報告には、次のスレッドから新しいフローで動くことと、フックの定義（`.codex/hooks.json`）が変わった場合は Settings > Hooks での信頼し直しが要ることを書く。

## 実機

ユーザーが「実機」「実機に入れろ」と言ったら、実機でその変更を確かめられる状態にすることが依頼。実装役に次を依頼し、終わったらすぐ報告する。

1. 計画の「変更箇所」から、変更が iOS アプリ側か、サーバー側（API・DB・Web）か、両方かを判定する。
2. iOS アプリ側の変更を含む: `ios-deploy` スキルで、対象ブランチを実機に入れる。
3. サーバー側の変更を含む: 実機の接続先（ポート3000）のサーバーが、その変更を含む版で動いているかを確かめる。含まなければ、対象ブランチをビルドし、ポート3000 のサーバーをその版で起動し直す。ただし、対象ブランチが `schema/` のマイグレーションを追加している場合は、起動し直さずに報告する（本番 DB へのマイグレーションは、ユーザーの明示的な指示があるときだけ行う）。
4. 報告には、何を入れたか（アプリ、サーバー）と、実機で変更が見える状態かどうかを書く。

実機に入れた後、頼まれていない確認を続けない。
