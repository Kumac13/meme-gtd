# 開発フロー（Codex）

meme-gtd の Task を起点に、検討 → 計画 → 実装 → 確認 → PR → レビューを直列に進める手順。このスキルがこの流れの唯一の正。

メインスレッド（窓口）は、ユーザーと話すことと進行の管理だけを行う。計画・実装・確認・レビューは `spawn_agent` で、`fork_turns="none"` の別文脈に渡す（同じ文脈で続けると、検討時の誤った前提が実装とレビューまで残るため）。

## 分担

ユーザーが介入するのは次の3つだけ。窓口が自分から応答を終えて待つのも、この3つのときだけ。
- 計画の承認（3）。毎回1度、チャットに計画の全文を出して承認を得る。承認の前に実装へ進まない。
- Task の本文とご指摘からは決まらない方針の決定（「質問の形」の条件を満たすものだけ）
- UI の変更後のスクショでの確認（5）

それ以外は聞かずに進める: 調査、コードの追跡、方式の比較、計画の作成とチェック、ブランチ作成、実装、テスト、画面での確認、スクショ撮影、Task への記録、push、PR 作成、PR のリンク登録、レビュー、マージ後のローカル更新と本番サーバーの再起動。

検討の結果を返しただけで応答を終えない。「検討」と言われた場合も、調査 → 計画 → 計画チェックまでを同じ応答の中で進め、計画の提示で止まる（Task 2107 で、検討結果だけを返して止まり「なんで止まってんだ」とご指摘を受けたため）。

## 依頼された範囲

- Task の本文に書いてあることは、決定済みとして扱う。本文にある対象・条件を、質問や「確認」として聞き返さない（Task 2107 の本文に「memoやTask,Articlesのログ」とあるのに対象範囲を聞き、ご指摘を受けたため）。
- 本文に無い対象や条件を、検討事項として足さない（同 Task で、全体の Activity Log への適用と、解除までの経過時間という条件を足したため）。足したくなった点は、計画の「合意」に「本文に無いので行わない」と1行で書く。
- ユーザーがチャットで単発の作業を頼んだとき（「実機に入れて」「サーバーを再起動して」など）は、その作業だけを行い、終わった時点で結果を報告する。頼まれていない確認・検証・調査を続けて起動しない（Task 2107 で、実機へのインストール成功後に依頼外の確認を起動し、20分以上報告しなかったため）。手順は「9. 単発の依頼」。

## 窓口ができること（フックで強制）

窓口が実行できるのは、読み取り系のコマンド（`git status`・`git diff`・`git log`・`rg`・`gh pr view` など）と `scripts/task.mjs`・`scripts/checklist.mjs` だけ。それ以外（編集・ビルド・テスト・シミュレーター・push・PR 作成）は `.codex/hooks/orchestrator-guard.mjs` が拒否する。拒否されたら、該当する役割に渡す。

- サブエージェントを待つ前に、何を誰に渡したか、何が返ってきたら次に何をするかを、チャットに1〜2行で書く（待機中はユーザーに何も見えないため）。
- サブエージェントを待つときは、`wait_agent` を最大の `timeout_ms`（3600000）で1回呼ぶ。短い間隔で待ち直さない（待ち直すたびに窓口の文脈全体が送り直され、トークンを消費するため）。ユーザーが発言すると、待機はその時点で終わる。
- 役割から完了報告が返ったら、次の役割を起動する前に、その結果をチャットに書く。
- 役割に渡すのは、このフローが定めた作業だけ。依頼にもフローにも無い作業のために役割を起動しない。
- 途中経過の確認のために `send_message` を送らない。役割から返ってきた完了報告だけで次へ進む。

## 指摘一覧（状態表）

ユーザーのご指摘は、Task の固定コメント1件（`## 指摘一覧`）に1件1行で記録する。行は消さず、状態・根拠・次だけを更新する。操作は `scripts/task.mjs status` だけを使う。

- 受付時に `status <TaskID> init` で作る。Task の本文とコメントにあるご指摘を、原文のまま `status add` する。
- ユーザーの発言（チャットまたは Task へのコメント）に新しいご指摘が含まれていたら、作業の前に原文のまま `status add` する。言い換えない、まとめない、狭めない。
- 各役割に渡す前と、ユーザーへ報告する前に、`task.mjs read` で Task のコメントを読み直し、取り込んでいないご指摘がないか確かめる。
- 状態は `未着手 / 対応中 / 確認済み / 未確認 / 対象外` のどれか。`確認済み` は、確認役が実操作した証拠（スクショのパス）か自動テスト名があるときだけ。`対象外` は、ユーザーが対象外と決めたときだけ。

## 報告の形

Task への記録と、チャットでの報告は別のもの。Task のコメントは作業の記録で、ユーザーが判断に使うのはチャットの報告。ユーザーが判断・確認に必要な内容は、チャットにそのまま書く。「Task に記録しました」「コメント 2673 を参照」のように、記録の場所だけを伝えて内容を省かない（Task 2107 で、計画を Task に記録した旨だけを伝え、「なんでここで報告しないんだ」とご指摘を受けたため）。

- 最初の1文は、ユーザーの問いへの結論にする。
- ユーザーが書いた要求を言い直すだけの報告にしない。報告に書くのは、要求に対して窓口と各役割が出したもの（採用した方式と理由、変更する／した箇所と処理、確認の方法と結果、チェックした役割と結果）。
- ご指摘への対応を報告するときは、状態表の該当行（番号・ご指摘の原文・状態・根拠・次）を添える。原文は状態表のまま写し、自分の言葉に置き換えない。変化の無い行は並べない。
- 「一部対応」のような曖昧な状態は使わない。分けられるなら行を分けて、それぞれの状態を書く。
- 変更後の画面に関わる報告は、スクショを `![何の画面のどの状態か](絶対パス)` で添える（ユーザーはリモートから見ていることが多く、ファイルへのリンクは開けない）。変更前（現行）の画面は、ユーザーが求めたときだけ出す。
- Codex の画面では表を使ってよいが、Task のコメントには表を使わない（iOS アプリは Markdown の表を表示できず、`task.mjs` も投稿を拒否する）。

## 質問の形

質問してよいのは、次の3つをすべて満たす点だけ。満たす点が無ければ、質問は0件で計画に進む。
- Task の本文・コメント・ご指摘のどこにも答えが書かれていない
- 答えによって、利用者から見える結果（挙動・見た目・名称・対象範囲）が変わる
- コードと Web の調査では決まらない

質問するときの形:
1. 設問ごとに、Task のどの記述からは決まらないのか（本文の該当箇所の引用）と、何が起きたか（背景）を、一目で分かる長さで書く。
2. `request_user_input_async` で1問ずつ出す。範囲を決める問いを、順番を決める問いより先に出す。
3. 選択肢ごとに、効く点と弱い点を書く。選択肢に「推奨」の印を付けない。別々に決めるべきことを1つの選択肢にまとめない。
4. 選択肢の見た目の違いをユーザーが選ぶ問いにだけ、その違いが写ったスクショを添える。現行の画面をそのまま見せるだけのスクショは撮らない。

実装の方式（どの層で、どの処理順で実現するか）はユーザーに選ばせない。計画役が比較して決め、理由を計画に書く。自分の誤りの直し方もユーザーに選ばせず、依頼どおりに直してから報告する。

## Task への記録

`scripts/task.mjs` だけを使う（使い方: `node .codex/skills/dev-flow/scripts/task.mjs help`、詳しくは `references/task-log.md`）。`curl` で API に直接書き込まない。Task の Body と status は、ユーザーの指示があるときだけ変更する。

## 1. 受付

1. `task.mjs read` で、Task の本文・コメント・リンクを全部読む。貼られた JSON より、Task の現在の内容を正とする。
2. `task.mjs status <TaskID> init` で状態表を作り、ご指摘を原文のまま追加する。
3. 開始地点を決める。どの場合も、止まるのは 3 の計画の承認。
   - 承認済みの計画がある（`## 承認` のコメントが最新の計画より後にある）: 4 へ進む。
   - それ以外（「検討」「調査」「計画」「実装」「直して」、または Task を共有されただけ）: 2 から始め、3 の承認まで続けて進める。

## 2. 検討（計画役に渡す）

目的は、計画に必要な事実と方式の候補をそろえること。ファイルは変更しない。ユーザーへの中間報告のために止まらない。

1. 調査は計画役に渡す（窓口は調査コマンドを重ねて文脈を膨らませない）。調査には次の両方を含める。
   - Web 調査。iOS は Apple のドキュメントを参照する。見た目に関わる場合は、Human Interface Guidelines と `ios/README.md` のデザインシステム節を必ず読む。
   - 変更先のコード調査。
2. Task が挙げた選択肢は、すべて比較に入れる。
3. 現行の画面のスクショは撮らない（ユーザーは現行の画面を知っている。Task 2107 で現行画面3枚を出し、「現行表示を出す必要ないだろ」とご指摘を受けたため）。スクショを撮るのは、「質問の形」4 の場合と、5 の変更後の確認だけ。
4. 「質問の形」の条件を満たす点があれば、その点だけを聞く。無ければ、そのまま 3 へ進む。

## 3. 計画（計画役 → 計画チェック → ユーザーの承認）

1. `spawn_agent`（`fork_turns="none"`）で計画役を起動し、`roles/planner.md` を読ませる。渡すのは Task ID と、ユーザーが答えた決定だけ。2 の調査と同じ計画役に続けて頼んでよい。計画役が `task.mjs comment --kind plan` で計画を Task に記録する。
2. 計画役とは別に、`spawn_agent`（`fork_turns="none"`）でレビュー役を起動し、`roles/reviewer.md` の「計画チェック」を行わせる。渡すのは Task ID だけ。レビュー役が `task.mjs comment --kind plan-check` で結果を記録する。指摘があれば計画役に戻し、計画を記録し直してから、新しいレビュー役でチェックし直す。
3. チャットに計画を出す。Task に記録した旨ではなく、次の内容そのものを書く（Task 2107 で、要求の言い直しだけを出し、「計画？ユーザが書いた要求の話ししかしてない」「適当な方法か検討した結果なのか？だれがチェックした？」とご指摘を受けたため）。
   - 採用した方式と、比較した他の候補、それぞれを採らなかった理由
   - 変更するファイルと、処理の内容・順序（例: どの読み取りで、何を条件に、件数制限の前後どちらで除外するか）
   - 確認の方法（自動テストで何を判定するか、実画面でどの操作を確認するか）
   - 反映先（変更が見えるようになるのに必要なもの: iOS アプリの入れ直し／ポート3000の本番サーバーの再起動／DB マイグレーション）
   - 誰がチェックしたか（計画役・レビュー役それぞれが確認したことと、レビュー役の指摘への対応）
   - 本文に無いので行わないこと
4. ユーザーの承認を待つ。承認の言葉が来たら、`task.mjs approve <TaskID> --words "<ユーザーの承認の原文>"` で記録してから 4 へ進む。
   - 承認が記録されていない Task では、実装役の着手記録（`comment --kind start`）を `task.mjs` が拒否する。拒否されたら、承認を自分で作らずに、ここへ戻る。
   - 計画を記録し直した場合、前の承認は効かない。チャットに出し直して、承認を取り直す。
   - 承認になるのは、提示した計画に対する承認の言葉（「OK」「進めて」「承認」など）だけ。計画を出す前の「実装して」や、別の話題への返事を承認として記録しない（Task 2107 で、承認の無いまま実装へ進み、「計画を承認してないけど」とご指摘を受けたため）。
5. 粒度を分ける場合は、計画役が `task.mjs create --parent` でサブ Task を作る。承認は、計画を記録した Task ごとに取る。

## 4. 実装（実装役、粒度ごとに直列）

1. 粒度ごとに `spawn_agent`（`fork_turns="none"`）で実装役を起動し、`roles/implementer.md` を読ませる。渡すのは対象の Task ID だけ。
2. 実装役は、実装・自動テスト・push 前の検証まで行い、確認一覧（JSON）を作って返す。画面の確認は実装役ではなく確認役が行う。
3. 実装役の報告に、ゴールの範囲外の気づきがあれば、状態表に追加するかをユーザーに聞く。

## 5. 確認（確認役）

1. `spawn_agent` で `agent_type="verifier"`・`fork_turns="none"` を指定して確認役を起動する。渡すのは Task ID、実装のブランチと worktree のパス、確認一覧のパスだけ（実装役の説明は渡さない）。
2. 確認役は、確認一覧の全行を実画面で操作し、結果とスクショを記録する。全行がそろうまで、`.codex/hooks/verifier-stop.mjs` が終了を差し戻す。
3. 窓口は `checklist.mjs check <確認一覧>` で結果を確かめ、`fail` の行を実装役に戻す。修正後は、確認役を新しく起動して全行を確認し直す。前回の結果は合格に数えない。
4. UI の変更を含む場合は、確認役のスクショを `view_image` で見て、`references/ui-evidence.md` の提出前点検を行う。通ったものを、どのご指摘・確認基準を確認できる画像かを添えてユーザーにインラインで出し、確認を得る。修正の指示は実装役に渡す。

## 6. PR（実装役）

1. 確認とユーザーの確認（UI を含む場合）が済んだら、実装役に push と PR 作成を依頼する。このフローで実装を依頼された時点で、PR 作成までが依頼に含まれる（`release` スキルの「Push は明示的な指示がある場合のみ」は、この依頼で満たされる）。
2. ベースは `main`。push 前の検証は、ルート `CLAUDE.md`「Push前のローカル検証」に従う。
3. 実装役が、PR を作った直後に `task.mjs link-pr <TaskID> --url <PR URL>` で、その粒度の Task に外部リンク（表示名 `PR`）を登録する。
4. 窓口は、PR の URL をユーザーに伝える前に、`task.mjs read` の `urlLinks` に表示名 `PR` のリンクがあることを確かめる。無ければ、自分で `link-pr` を実行してから伝える（Task 2107 で、PR を伝えた時点で Task にリンクが無く、「リンクにprないけど」とご指摘を受けたため）。リンクが無い Task では、レビュー結果の記録（`comment --kind review`）を `task.mjs` が拒否する。

## 7. レビュー（レビュー役、PR ごと）

1. PR 作成後、`spawn_agent`（`fork_turns="none"`）でレビュー役を起動し、`roles/reviewer.md` を読ませる。渡すのは PR 番号と、その粒度の Task ID だけ。
2. 指摘のうち、ゴールと確認基準の範囲内の修正は実装役に渡し、修正後は 5 の確認からやり直す。ユーザーの判断が必要なものは、「質問の形」に従って1問ずつ聞く。
3. レビュー結果は、レビュー役が `task.mjs comment --kind review` で記録する。窓口は状態表を更新し、「報告の形」に従って、レビューの結論・指摘の内容と対応・PR の URL をチャットで報告する。

## 8. マージ後

ユーザーが「merged」と伝えたら、読み取り系のコマンドでマージを確認する。ローカルの `main` の更新は、実装役に依頼する。未コミットの変更がある作業ツリーには触れない。

変更がサーバー側（`packages/api`・`packages/core`・`packages/db`・`packages/shared`・`packages/web`）を含む場合は、続けて `references/prod-server.md` の手順で、ポート3000の本番サーバーを更新後の `main` から再起動させ、その結果を報告する（Web と iOS の Server モードは、このサーバーが返す内容を表示する。Task 2107 で、サーバーが古い作業ツリーのまま動いていて変更が表示されず、「何も消えてないが」「さっさとサーバー立ち上げ直せよ」とご指摘を受けたため）。

## 9. 単発の依頼

フローの途中でユーザーが単発の作業を頼んだときは、`spawn_agent`（`fork_turns="none"`）で作業役を1つ起動し、その作業の手順だけを渡す。終わったら結果を報告して、元の位置に戻る。

- 「実機に入れて」「シミュレーターに入れて」: `ios-deploy` スキルの手順だけを行わせる。インストールの成否が出た時点で終了させ、すぐ報告する。動作の確認は、頼まれていなければ行わない。
- 入れる版がサーバー側の変更を含む場合は、`references/prod-server.md` の「実機で見る」に従う。iOS アプリを入れ直しただけでは、サーバー側の変更は実機に表示されない。
- 「サーバーを再起動して」「立ち上げ直して」: `references/prod-server.md` の手順を行わせる。
