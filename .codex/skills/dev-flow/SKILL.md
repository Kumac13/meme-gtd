# 開発フロー（Codex）

meme-gtd の Task を起点に、検討 → 計画 → 実装 → PR → レビューを直列に進める手順。このスキルがこの流れの唯一の正。

メインスレッドは窓口で、ユーザーと話すのは窓口だけ。計画・実装・レビューは `spawn_agent` で別の文脈に渡す（同じ文脈で続けると、検討時の誤った前提が実装とレビューまで残るため）。

## 分担

ユーザーが決めること: どうあるべきか（挙動・見た目・名称・対象範囲・やらないこと）。窓口と各役割は、これを推測で埋めずに聞く。何を決めるべきかの一覧も、ユーザーの言葉と調査結果から出てきたものだけにする。

窓口と各役割が聞かずに進めること: 調査、コードの追跡、ブランチ作成、テスト、画面での自己確認、スクショ撮影、Task への記録、PR 作成、レビュー依頼、マージ後のローカル更新。

## 共通ルール

- 質問は `request_user_input_async` で1問ずつ出す。設問の中に、背景と、各選択肢がなぜ候補なのかを一目で分かる長さで書く。
- 自分の誤りの直し方はユーザーに選ばせず、依頼どおりの状態に直してから報告する。
- 報告は最初の1文を結論にする。検討中は、追加の指摘に答えるときも、最初の問いへの結論を先頭に置く（指摘された点だけを答えると問いが失われるため）。
- 画像は `![説明](絶対パス)` でインライン表示する。ユーザーはリモートから見ていることが多く、ファイルへのリンクは開けない。
- 作業を止めるときは、止める理由と再開に必要なものを書く。
- Task への読み書きは `references/task-log.md` の手順だけを使う。Task の Body と status は、ユーザーの指示があるときだけ変更する。
- 依頼にない表示・機能・設定変更を足さない。必要だと考えたら、変更せずに窓口経由でユーザーに聞く。

## 1. 受付

1. `references/task-log.md` の手順で、Task の本文・コメント・リンクを全部読む。貼られた JSON より Task の現在の内容を正とする。
2. 開始地点を決める。
   - 依頼に「実装」とある: 4 へ進む。ゴールと確認基準がまだ無ければ 3 から始める。
   - 依頼に「検討」「調査」とある: 2 へ進む。
   - どちらも無い: ファイルを変更しない調査を始めながら、検討と実装のどちらかを1問で聞く。答えが来るまでファイルは変更しない。
3. ユーザーの問いを1〜2文で言い直し、最初の応答に含める。以後の報告はこの問いに答える形にする。

## 2. 検討（窓口とユーザー）

目的は、ユーザーが「どうあるべきか」を決めるための材料を出すこと。ファイルは変更しない。

1. 調査は次の両方を行う。
   - Web 調査。iOS は Apple のドキュメントを参照し、見た目に関わる場合は Human Interface Guidelines と `ios/README.md` のデザインシステム節を必ず読む。
   - 変更先のコード調査。
2. Task が挙げた選択肢（既存実装の破棄など）は、すべて比較に入れる。既存実装を残す前提から始めない。
3. ユーザーから指摘や追加要件が来たら、該当箇所を調査し直してから答える。
4. UI の検討は `references/ui-evidence.md` の手順で撮った実画面のスクショで行う。モックは使わない。
5. 次の3点が決まったら検討を終える。決まっていない点は1問ずつ聞く。
   - どの粒度に分けるか
   - 粒度ごとのゴール（何がどうできているか）
   - 粒度ごとの確認基準（何が確認できれば、できていると言えるか）

## 3. 計画（別文脈）

1. `spawn_agent` を `fork_turns="none"` で呼び、`roles/planner.md` を読ませる。渡すのは Task ID と、検討で決まったことだけ。
2. 計画役は、実装時に方針変更が入らないよう、変更経路を端から端までコードで確認する。未決事項は決めずに窓口へ返す。
3. 窓口は未決事項を1問ずつ聞く。
4. 粒度ごとに `references/task-log.md` の手順でサブ Task を作り、Body にゴールと確認基準を書く。分割が不要な場合はサブ Task を作らず、元の Task にコメント1件でゴールと確認基準を書く。
5. 計画はユーザーの承認を待たずに 4 へ進む。計画の全文は Task に置き、ユーザーへの報告は粒度の一覧だけにする。

## 4. 実装（別文脈、粒度ごとに直列）

1. 粒度ごとに `spawn_agent` を `fork_turns="none"` で呼び、`roles/implementer.md` を読ませる。渡すのは対象の Task ID だけ。
2. 実装役の完了報告を受けたら、確認基準ごとの結果を読む。未確認の項目があれば、実装役に確認を続けさせる。
3. UI の変更を含む場合は、実装役が撮ったスクショを窓口が `view_image` で見て、`references/ui-evidence.md` の提出前点検を行う。通ったものをユーザーにインラインで提出し、確認を得る。修正の指示は同じ実装役に渡す。
4. PR を作成する。このフローで実装を依頼された時点で、PR 作成までが依頼に含まれる（`release` スキルの「Push は明示的な指示がある場合のみ」は、この依頼で満たされる）。
   - UI の変更を含む場合は、3 の確認を得てから push する。
   - ベースは `main`。push 前の検証はルート `CLAUDE.md`「Push前のローカル検証」に従う。
   - PR の URL を `references/task-log.md` の手順で Task の外部リンクに登録する。

## 5. レビュー（別文脈）

1. PR 作成後、`spawn_agent` を `fork_turns="none"` で呼び、`roles/reviewer.md` を読ませる。渡すのは PR 番号と Task ID だけ。
2. 指摘のうち、ゴールと確認基準の範囲内の修正は実装役に渡す。ユーザーの判断が必要なものは1問ずつ聞く。
3. レビュー結果と対応を Task にコメントし、ユーザーには結論と PR の URL を報告する。

## 6. マージ後

ユーザーが「merged」と伝えたら、マージを確認し、ローカルの `main` を最新にして、作業用の worktree とブランチを片付ける。未コミットの変更がある作業ツリーには触れない。
