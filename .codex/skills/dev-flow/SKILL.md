# 開発フロー（Codex）

meme-gtd の Task を起点に、検討 → 計画 → 実装 → 確認 → PR → レビューを直列に進める手順。このスキルがこの流れの唯一の正。

メインスレッド（窓口）は、ユーザーと話すことと進行の管理だけを行う。計画・実装・確認・レビューは `spawn_agent` で、`fork_turns="none"` の別文脈に渡す（同じ文脈で続けると、検討時の誤った前提が実装とレビューまで残るため）。

## 分担

ユーザーが介入するのは次の2つだけ。
- 方針の決定: どうあるべきか（挙動・見た目・名称・対象範囲・やらないこと）
- このフローが定めた確認: 仕様判断を含む計画の合意（3）、UI のスクショでの確認（5）

それ以外は聞かずに進める: 調査、コードの追跡、ブランチ作成、実装、テスト、画面での確認、スクショ撮影、Task への記録、push、PR 作成、レビュー、マージ後のローカル更新。

何を決めるべきかの一覧も、ユーザーの言葉と調査結果から出てきたものだけにする。

## 窓口ができること（フックで強制）

窓口が実行できるのは、読み取り系のコマンド（`git status`・`git diff`・`git log`・`rg`・`gh pr view` など）と `scripts/task.mjs`・`scripts/checklist.mjs` だけ。それ以外（編集・ビルド・テスト・シミュレーター・push・PR 作成）は `.codex/hooks/orchestrator-guard.mjs` が拒否する。拒否されたら、該当する役割に渡す。

- サブエージェントを待つときは、`wait_agent` を最大の `timeout_ms`（3600000）で1回呼ぶ。短い間隔で待ち直さない（待ち直すたびに窓口の文脈全体が送り直され、トークンを消費するため）。ユーザーが発言すると、待機はその時点で終わる。
- 途中経過の確認のために `send_message` を送らない。役割から返ってきた完了報告だけで次へ進む。

## 指摘一覧（状態表）

ユーザーのご指摘は、Task の固定コメント1件（`## 指摘一覧`）に1件1行で記録する。行は消さず、状態・根拠・次だけを更新する。操作は `scripts/task.mjs status` だけを使う。

- 受付時に `status <TaskID> init` で作る。Task の本文とコメントにあるご指摘を、原文のまま `status add` する。
- ユーザーの発言（チャットまたは Task へのコメント）に新しいご指摘が含まれていたら、作業の前に原文のまま `status add` する。言い換えない、まとめない、狭めない。
- 各役割に渡す前と、ユーザーへ報告する前に、`task.mjs read` で Task のコメントを読み直し、取り込んでいないご指摘がないか確かめる。
- 状態は `未着手 / 対応中 / 確認済み / 未確認 / 対象外` のどれか。`確認済み` は、確認役が実操作した証拠（スクショのパス）か自動テスト名があるときだけ。`対象外` は、ユーザーが対象外と決めたときだけ。

## 報告の形

ユーザーへの報告は、状態表と同じ形にする。

```markdown
| # | ご指摘（原文） | 状態 | 根拠 | 次 |
```

- 最初の1文は、ユーザーの問いへの結論にする。
- ご指摘を自分の言葉に置き換えない。原文の列は状態表のまま写す。
- 「一部対応」のような曖昧な状態は使わない。分けられるなら行を分けて、それぞれの状態を書く。
- 画面に関わる行は、スクショを `![何の画面のどの状態か](絶対パス)` で添える（ユーザーはリモートから見ていることが多く、ファイルへのリンクは開けない）。

## 質問の形

1. まず、何を決めるかの論点の一覧をユーザーと合意する。論点の選び方そのものがユーザーの領分なので、合意の前に選択肢を出さない。
2. 合意した論点ごとに、`request_user_input_async` で1問ずつ出す。範囲を決める問いを、順番を決める問いより先に出す。
3. 設問には、何が起きたか（背景）を一目で分かる長さで書く。選択肢ごとに、効く点と弱い点を書く。
4. 選択肢に「推奨」の印を付けない。別々に決めるべきことを1つの選択肢にまとめない。
5. UI に関わる問いには、該当画面のスクショを添える。

自分の誤りの直し方はユーザーに選ばせず、依頼どおりに直してから報告する。

## Task への記録

`scripts/task.mjs` だけを使う（使い方: `node .codex/skills/dev-flow/scripts/task.mjs help`、詳しくは `references/task-log.md`）。`curl` で API に直接書き込まない。Task の Body と status は、ユーザーの指示があるときだけ変更する。

## 1. 受付

1. `task.mjs read` で、Task の本文・コメント・リンクを全部読む。貼られた JSON より、Task の現在の内容を正とする。
2. `task.mjs status <TaskID> init` で状態表を作り、ご指摘を原文のまま追加する。
3. 開始地点を決める。
   - 依頼が実装を求めている（「実装」「直して」「作って」など）: 4 へ進む。ゴールと確認基準がまだ無ければ 3 から始める。
   - 依頼が検討や調査を求めている: 2 へ進む。
   - どちらとも読み取れない: ファイルを変更しない調査を始めながら、検討と実装のどちらかを1問で聞く。答えが来るまでファイルは変更しない。

## 2. 検討（窓口とユーザー）

目的は、ユーザーが「どうあるべきか」を決めるための材料を出すこと。ファイルは変更しない。

1. 調査は計画役に渡す（窓口は調査コマンドを重ねて文脈を膨らませない）。調査には次の両方を含める。
   - Web 調査。iOS は Apple のドキュメントを参照する。見た目に関わる場合は、Human Interface Guidelines と `ios/README.md` のデザインシステム節を必ず読む。
   - 変更先のコード調査。
2. Task が挙げた選択肢は、すべて比較に入れる。
3. UI の検討は、`references/ui-evidence.md` の手順で撮った実画面のスクショで行う。モックは使わない。
4. 決めることは「質問の形」に従って、1問ずつ聞く。

## 3. 計画（計画役）

1. `spawn_agent`（`fork_turns="none"`）で計画役を起動し、`roles/planner.md` を読ませる。渡すのは Task ID と、検討で決まったことだけ。
2. 計画役の返す「仕様判断」を見る。
   - 仕様判断を含む（挙動・見た目・名称・対象範囲のどれかを、Task とご指摘に無い形で決める必要がある）: ゴールと確認基準を1問で提示し、合意を取ってから 4 へ進む。
   - 含まない（既存の仕様どおりに直すだけ）: 合意を取らずに 4 へ進む。
3. 計画役が `task.mjs comment --kind plan` で計画を Task に記録する。粒度を分ける場合は、計画役が `task.mjs create --parent` でサブ Task を作る。
4. ユーザーへの報告は、粒度の一覧と、合意が必要な点だけにする。計画の全文は Task に置く。

## 4. 実装（実装役、粒度ごとに直列）

1. 粒度ごとに `spawn_agent`（`fork_turns="none"`）で実装役を起動し、`roles/implementer.md` を読ませる。渡すのは対象の Task ID だけ。
2. 実装役は、実装・自動テスト・push 前の検証まで行い、確認一覧（JSON）を作って返す。画面の確認は実装役ではなく確認役が行う。
3. 実装役の報告に、ゴールの範囲外の気づきがあれば、状態表に追加するかをユーザーに聞く。

## 5. 確認（確認役）

1. `spawn_agent` で `agent_type="verifier"`・`fork_turns="none"` を指定して確認役を起動する。渡すのは Task ID、実装のブランチと worktree のパス、確認一覧のパスだけ（実装役の説明は渡さない）。
2. 確認役は、確認一覧の全行を実画面で操作し、結果とスクショを記録する。全行がそろうまで、`.codex/hooks/verifier-stop.mjs` が終了を差し戻す。
3. 窓口は `checklist.mjs check <確認一覧>` で結果を確かめ、`fail` の行を実装役に戻す。修正後は、確認役を新しく起動して全行を確認し直す。前回の結果は合格に数えない。
4. UI の変更を含む場合は、確認役のスクショを `view_image` で見て、`references/ui-evidence.md` の提出前点検を行う。通ったものを、状態表の形でユーザーにインラインで出し、確認を得る。修正の指示は実装役に渡す。

## 6. PR（実装役）

1. 確認とユーザーの確認（UI を含む場合）が済んだら、実装役に push と PR 作成を依頼する。このフローで実装を依頼された時点で、PR 作成までが依頼に含まれる（`release` スキルの「Push は明示的な指示がある場合のみ」は、この依頼で満たされる）。
2. ベースは `main`。push 前の検証は、ルート `CLAUDE.md`「Push前のローカル検証」に従う。
3. 窓口が `task.mjs link-pr <TaskID> --url <PR URL>` で、その粒度の Task に外部リンク（表示名 `PR`）を登録する。

## 7. レビュー（レビュー役、PR ごと）

1. PR 作成後、`spawn_agent`（`fork_turns="none"`）でレビュー役を起動し、`roles/reviewer.md` を読ませる。渡すのは PR 番号と、その粒度の Task ID だけ。
2. 指摘のうち、ゴールと確認基準の範囲内の修正は実装役に渡し、修正後は 5 の確認からやり直す。ユーザーの判断が必要なものは、「質問の形」に従って1問ずつ聞く。
3. レビュー結果は、レビュー役が `task.mjs comment --kind review` で記録する。窓口は状態表を更新し、状態表の形で結論と PR の URL を報告する。

## 8. マージ後

ユーザーが「merged」と伝えたら、読み取り系のコマンドでマージを確認する。ローカルの `main` の更新は、実装役に依頼する。未コミットの変更がある作業ツリーには触れない。
