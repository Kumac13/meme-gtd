# 本番サーバー（ポート3000）の再起動

Web（http://localhost:3000）と、iOS アプリの Server モード（実機を含む）は、ポート3000の本番サーバーが返す内容を表示する。サーバー側（`packages/api`・`packages/core`・`packages/db`・`packages/shared`・`packages/web`）の変更は、その変更を含むコードでこのサーバーをビルドして再起動するまで、どの画面にも出ない。iOS アプリを入れ直しても変わらない。

Task 2107 では、PR をマージする前に実機へアプリを入れ、サーバーは別の作業ツリー（Task 2109）のコードで動いたままだったため、変更が表示されなかった。

`test-env` スキルの「ポート3000へのアクセス禁止」は、検証・テストのデータ操作の話。ここで行うのは、プロセスの再起動と `/api/health` の確認だけで、本番のデータは読み書きしない。`mgtd` の直接実行は引き続き禁止。

## いつ行うか

- マージ後（SKILL.md 8）: 変更がサーバー側を含むとき。ユーザーに聞かずに行う。
- ユーザーが「サーバーを再起動して」「立ち上げ直して」と言ったとき。
- 「実機で見る」（下記）に当たるとき。

窓口はこの手順のコマンドを実行できない（フックが拒否する）。`spawn_agent`（`fork_turns="none"`）で作業役を起動して、この手順を渡す。

## 手順

1. いま動いているサーバーと、その作業ツリーを調べる。

```bash
lsof -nP -iTCP:3000 -sTCP:LISTEN
lsof -a -p <PID> -d cwd
git -C <その作業ツリー> log -1 --format='%h %s'
```

2. 起動するコードを決める。マージ後は、メインの作業ツリーの更新後の `main`。マージ前に実機で見る場合は、その PR の worktree。
3. DB マイグレーション（`schema/` の追加）を含む変更は、ここで止めて窓口に返す。本番 DB へのマイグレーションは、ユーザーの明示的な指示があるときだけ行う（`db-migration` スキル）。
4. 起動するコードの作業ツリーでビルドする。

```bash
pnpm install --frozen-lockfile
pnpm build
```

5. 動いているサーバーを止め、起動し直す。ターミナルを閉じても動き続けるように起動し、出力はログに残す。

```bash
kill <PID>
mkdir -p ~/.local/state/mgtd
nohup pnpm server:start > ~/.local/state/mgtd/server-3000.log 2>&1 &
```

   launchd や systemd でサーバーを管理している場合（1 の親プロセスが `launchd`／`systemd` で、止めても自動で起動し直される場合）は、`kill` と `nohup` の代わりに、そのサービスを再起動する。

6. 起動を確かめる。

```bash
curl -fsS http://localhost:3000/api/health
lsof -a -p <新しい PID> -d cwd
```

7. 窓口に返す内容: 再起動の前後それぞれの、作業ツリーのパスとコミット。`/api/health` の応答。失敗した場合は、失敗した段階（調査・ビルド・停止・起動・確認）とログの末尾。

## 実機で見る

ユーザーが「実機に入れて」と頼み、入れる版がサーバー側の変更を含む場合:

1. `ios-deploy` スキルでアプリを入れる。
2. 続けて、この手順でサーバーを、その変更を含むコードから再起動する（ユーザーが実機で見たいのは変更後の表示で、アプリの入れ直しだけでは出ないため）。手順 3 に当たる場合は、再起動せずに、マイグレーションが必要であることを報告する。
3. 報告の最初の1文で、アプリのインストールの成否と、サーバーがどのコミットで動いているかの両方を書く。サーバーを再起動できなかった場合は、「サーバー側の変更は、まだ実機に表示されない」と明記する。
4. マージ前の worktree からサーバーを起動した場合は、その旨を報告に書き、マージ後に `main` から起動し直す（SKILL.md 8）。
